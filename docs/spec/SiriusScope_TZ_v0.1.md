# Техническое задание на разработку программного комплекса SiriusScope

**Версия:** 0.1  
**Статус:** инженерный черновик для разработки  
**Назначение документа:** использование как основного технического задания при разработке SiriusScope, включая работу с ИИ-агентом Codex и ведение задач в GitHub.

---

## 1. Общие сведения

### 1.1. Наименование проекта

Наименование программного продукта: **SiriusScope**.

Название SiriusScope используется как рабочее название проекта, имя репозитория и основное наименование программного комплекса в рамках разработки.

### 1.2. Назначение SiriusScope

SiriusScope — принципиально новое кроссплатформенное программное обеспечение для изделия «Сириус», предназначенное для:

- управления аппаратной частью изделия;
- приема данных от блока цифровой обработки и поворотного устройства по сети;
- отображения сигналов в SpectrumView и WaterfallView;
- непрерывной регистрации данных между запусками программы;
- сканирования выбранного оператором сектора;
- вычисления и отображения пеленга по каждому частотному диапазону;
- отображения итоговых результатов сканирования в таблице;
- сохранения данных водопада, итоговой таблицы и настроек программы.

Главной функциональной задачей SiriusScope является **пеленгование сигнала**. Распознавание типа радиотехнического средства не входит в текущую итерацию и рассматривается как перспективное расширение.

### 1.3. Основание для разработки

Разработка SiriusScope выполняется в рамках задачи создания программного комплекса для обработки, визуализации и регистрации параметров сигналов в реальном времени для изделия «Сириус».

Изделие «Сириус» относится к комплексам радиотехнической разведки и предназначено для обнаружения, приема и анализа сигналов радиотехнических средств, определения направления на источники радиоизлучений, измерения частотно-временных и амплитудных параметров сигналов.

Исходные документы по проекту фиксируют необходимость объединения функций управления изделием и анализа сигналов в едином программном комплексе, а также необходимость использования спектрально-временной визуализации в виде водопада и кругового индикатора пеленга.

### 1.4. Границы текущей версии ТЗ

Текущее ТЗ описывает всю систему SiriusScope как продукт, по которому будет выполняться разработка.

В текущую итерацию входят:

- архитектура SiriusScope с нуля;
- прием данных по TCP/UDP;
- поддержка аппаратуры и имитационного генератора через одинаковый протокол;
- управление БЦО и поворотным устройством через инкапсулированные интерфейсы;
- SpectrumView, BandItem, WaterfallView, AntennaIndicator, MenuBar, StatusBar;
- непрерывное хранение данных;
- прокрутка истории водопада и итоговой таблицы;
- темная тема;
- тестовый генератор сигналов;
- покрытие исходного кода тестами не менее 50%.

В перспективное расширение вынесены:

- распознавание типа РТС;
- картографический фон;
- передача данных в сопряженные системы;
- экспорт итоговой таблицы;
- пользовательская настройка размеров всех виджетов;
- история обнаружений на пеленгаторе;
- поддержка антенны на 8 лучей;
- расширенные инструменты фильтрации, сортировки и анализа итоговой таблицы.

## 3. Общая архитектура SiriusScope

### 3.1. Архитектурный принцип

SiriusScope должен разрабатываться как модульное, расширяемое и кроссплатформенное ПО. Основная архитектурная идея — отделение пользовательского интерфейса, бизнес-логики, аппаратных протоколов и хранения данных.

Рекомендуемое разделение:

```text
UI layer
    MainWindow
    MenuBar
    SpectrumView
    BandItem
    WaterfallView
    AntennaIndicator
    ResultTableView
    StatusBar
    BandSettingsDialog

Application layer
    ApplicationController
    SessionController
    ScanController
    DeviceControlFacade
    WaterfallController
    ResultTableController
    SettingsService

Core / Domain layer
    SignalSample
    BeamSample
    BandConfig
    WaterfallRow
    BearingResult
    ScanSector
    TimeBase
    Processing services
    Bearing services

Infrastructure layer
    TcpAntennaClient
    UdpBcoReceiver
    ProtocolParserV1/V2/...
    BcoCommandAdapter
    AntennaCommandAdapter
    BinaryWaterfallStorage
    BinaryResultTableStorage
    JsonOrIniSettingsStorage
    DiagnosticLogStorage
```

Примечание: приведенная выше схема является ранним укрупненным разделением системы. В актуальной архитектурной документации аппаратные адаптеры и инфраструктура хранения разделяются на отдельные логические слои, а обработка сигналов и пеленгация выделяются в Processing Layer. При проектировании и реализации новых подсистем необходимо сверяться с `docs/architecture/layers.md`.

### 3.2. Инкапсуляция аппаратного взаимодействия

Функции управления аппаратной частью должны быть обязательно включены в SiriusScope, но не должны быть жестко связаны с GUI или доменной логикой.

Протоколы управления БЦО и поворотным устройством могут меняться. Поэтому все аппаратное взаимодействие должно быть скрыто за абстрактными интерфейсами.

Обязательные интерфейсные направления:

- интерфейс приема данных БЦО;
- интерфейс приема текущего азимута поворотного устройства;
- интерфейс управления БЦО;
- интерфейс управления поворотным устройством;
- интерфейс выбора версии протокола;
- интерфейс подключения к реальной аппаратуре или имитационному генератору.

SiriusScope не должен иметь отдельного интерфейса управления РПУ, не должен формировать команды РПУ и не должен подключаться к РПУ напрямую. Все параметры, которые влияют на работу РПУ, передаются только в БЦО через интерфейс управления БЦО. БЦО внутри аппаратного комплекса отвечает за применение этих параметров к РПУ.

Пример требования:

```text
SiriusScope не должен обращаться к конкретному протоколу аппаратуры напрямую из UI-слоя.
Все команды и входные кадры должны проходить через инфраструктурные адаптеры и версионированные парсеры протоколов.
```

### 3.3. Поддержка версий протоколов

SiriusScope должен поддерживать архитектурное расширение версий протоколов приема и передачи данных.

Требования:

- версия протокола должна быть представлена явно;
- новая версия протокола должна добавляться без переписывания UI и основной бизнес-логики;
- код парсинга пакетов должен быть изолирован в отдельных классах/модулях;
- обработка неподдерживаемой версии протокола должна приводить к диагностическому сообщению в статус-баре и логе;
- режим работы с имитационным генератором должен использовать те же интерфейсы, что и режим работы с аппаратурой.

### 3.4. Технологический стек

SiriusScope должен разрабатываться с использованием следующего стека:

- C++;
- Boost;
- Qt;
- QML;
- CMake;
- Conan.

Программный комплекс должен проектироваться как кроссплатформенный. Конкретный перечень целевых операционных систем уточняется в процессе разработки, но архитектура не должна содержать необоснованных зависимостей от одной ОС.

### 3.5. Многопоточность

SiriusScope должен быть многопоточным. Заморозка интерфейса при приеме, обработке, записи или отображении данных недопустима.

Минимальное разделение потоков:

- GUI-поток;
- поток приема UDP-данных от БЦО;
- поток TCP-взаимодействия с поворотным устройством;
- поток обработки и группировки отсчетов;
- поток формирования строк WaterfallView;
- поток записи данных в архив;
- при необходимости отдельный поток подготовки данных для GPU/OpenGL.

Обмен между потоками должен выполняться через потокобезопасные очереди, сигналы, слоты или иные контролируемые механизмы. GUI не должен напрямую выполнять тяжелую обработку входного потока.

### 3.6. Использование GPU/OpenGL

Для WaterfallView предпочтительно использовать GPU/OpenGL или другой аппаратно-ускоренный механизм отрисовки, чтобы снизить нагрузку на CPU.

Реализация должна учитывать поток входных данных до 90 МБ/с и необходимость сохранения отзывчивости интерфейса при частоте обновления GUI не менее 30 FPS.

## 4. Аппаратное взаимодействие и входные данные

### 4.1. Источники данных

SiriusScope получает данные от двух основных источников:

1. **Поворотное устройство** — TCP-подключение, передающее текущий азимут антенны.
2. **БЦО** — UDP-поток, передающий дискретные отсчеты сигнала.

SiriusScope должен функционально одинаково работать:

- с реальной аппаратурой;
- с имитационным генератором сигналов.

Реальная аппаратура и имитационный генератор должны использовать одинаковый протокол передачи данных.

### 4.2. Данные от поворотного устройства

Поворотное устройство передает по TCP текущее значение угла поворота антенны.

Требования:

- период поступления данных: каждые 100 мс;
- точность значения азимута: 0,1 градуса;
- значение должно отображаться в AntennaIndicator и использоваться при расчете пеленга;
- при потере TCP-соединения SiriusScope должен показать ошибку в статус-баре и продолжить корректную работу доступных подсистем.

### 4.3. Диапазон поворота антенны

Антенна имеет почти полный диапазон поворота, но содержит слепую зону между 170 и 190 градусами.

Требования:

- центр антенны не может находиться в зоне 170–190 градусов;
- при необходимости перехода из положения 170 градусов в положение 200 градусов антенна должна разворачиваться в другую сторону;
- боковой луч покрывает слепую зону;
- алгоритм управления поворотом должен учитывать недопустимость установки центра антенны в слепую зону.

Ноль градусов соответствует направлению антенны по умолчанию. При установке на корабле направление 0 градусов соответствует курсу корабля.

### 4.4. Данные от БЦО

БЦО передает по UDP дискретные отсчеты сигнала. UDP-пакеты имеют размер порядка 1500 байт и состоят из набора отсчетов.

Каждый отсчет должен содержать:

| Поле | Описание |
|---|---|
| sampleIndex | Номер отсчета от старта сеанса обработки. |
| frequencyOffsetHz | Частота в Гц относительно основной частоты соответствующего диапазона приема, настроенного через БЦО. |
| amplitude | Уровень амплитуды от 1 до 127 условных единиц. |
| beamIndex | Номер луча: 0 или 1. |

Текущая версия SiriusScope разрабатывается под антенну с двумя лучами. Архитектурно необходимо предусмотреть возможность будущей поддержки антенны с 8 лучами, но реализация 8 лучей не входит в текущую итерацию.

Управляющая конфигурация приема передается из SiriusScope в БЦО. БЦО на основе этой конфигурации управляет РПУ и собственными режимами обработки.

Конфигурация БЦО должна концептуально поддерживать:

- набор до 8 частотных диапазонов на стороне протокола БЦО;
- ровно 5 частотных диапазонов, используемых SiriusScope в текущей версии;
- время стояния на каждой частоте или диапазоне;
- параметры фильтров;
- тип поляризации;
- входные и выходные аттенюаторы;
- дополнительные параметры приема, необходимые БЦО для управления РПУ.

Точный формат управляющего протокола БЦО должен быть описан в отдельном документе. До появления этого документа реализация должна использовать изолированный интерфейс управления БЦО и не должна закладывать детали протокола в UI или доменную модель.

### 4.5. Амплитуда

Амплитуда сигнала передается от БЦО в условных единицах.

Требования:

- допустимый диапазон: от 1 до 127;
- отрицательные значения амплитуды невозможны;
- значение 0 не является допустимой амплитудой входного отсчета;
- любое значение вне диапазона 1–127 считается некорректным;
- некорректные значения должны отбрасываться или помечаться диагностическим флагом без аварийного завершения программы.

### 4.6. Частота

БЦО передает частоту относительно основной частоты соответствующего диапазона приема, заданного через управляющую конфигурацию БЦО.

Требования:

- входная частота приходит в Гц;
- частота отображается оператору в МГц;
- частотное смещение приходит в диапазоне ±250 МГц от основной частоты диапазона;
- абсолютная частота для отображения вычисляется как сумма основной частоты диапазона, переданной в БЦО, и входного частотного смещения;
- полный рабочий диапазон ПТК и SiriusScope: от 0,3 до 18 ГГц;
- БЦО работает в полосе 500 МГц;
- расширение обрабатываемой полосы до 2500 МГц выполняется за счет использования 5 полос по 500 МГц.

### 4.7. Время

БЦО передает номер отсчета от времени старта сеанса обработки. В БЦО предусмотрены команды старта и окончания сеанса обработки.

Для SiriusScope требуется единая модель времени, позволяющая одновременно:

- сохранить исходный номер отсчета БЦО;
- вычислять локальное время от начала записи;
- привязывать события к глобальному времени компьютера;
- корректно восстанавливать историю между запусками программы;
- синхронизировать SpectrumView, WaterfallView, AntennaIndicator и итоговую таблицу.

Рекомендуемая модель:

```cpp
struct TimeBase
{
    int64_t  recordingStartUtcNs;  // UTC-время начала записи, нс от Unix Epoch
    uint64_t firstSampleIndex;      // номер первого отсчета записи
    uint64_t samplePeriodNs;        // период одного отсчета, например 320 нс
};
```

Базовые формулы:

```text
localTimeNs  = (sampleIndex - firstSampleIndex) * samplePeriodNs
backwardCompatibleTime = sampleIndex * 3.2
```

При samplePeriodNs = 320:

```text
localTimeNs = (sampleIndex - firstSampleIndex) * 320
```

Для глобального времени:

```text
globalTimeNs = recordingStartUtcNs + localTimeNs
```

В интерфейсе WaterfallView слева должна отображаться шкала времени в формате текущего системного времени, удобном оператору: дата, часы, минуты, секунды. Для внутренних расчетов и хранения должны сохраняться исходный sampleIndex и параметры TimeBase.

## 5. Обработка сигналов

### 5.1. Общие требования

На вход SiriusScope из БЦО поступает сигнал, уже прошедший аппаратную фильтрацию и цифровую обработку. SiriusScope не должен повторно выполнять базовую ЦОС-фильтрацию, если она уже выполнена аппаратурой.

Основная обработка в SiriusScope:

- прием дискретных отсчетов;
- проверка корректности входных значений;
- группировка отсчетов в импульсы;
- группировка импульсов в пачки сигналов;
- вычисление основных характеристик радиосигнала;
- подготовка данных для WaterfallView;
- вычисление пеленга по двум лучам;
- формирование итоговой таблицы после сканирования сектора.

### 5.2. Группировка отсчетов

Дискретные отсчеты должны группироваться по следующим признакам:

- принадлежность к BandItem;
- частотное положение;
- время поступления;
- номер луча;
- наличие близких отсчетов во временно-частотной области.

Точная математическая модель группировки импульсов и пачек сигналов должна быть реализована в отдельном модуле обработки и не должна быть жестко связана с UI.

### 5.3. Пеленгование

Пеленгование является основной задачей SiriusScope.

Требования:

- расчет пеленга должен выполняться отдельно для каждого BandItem;
- расчет должен использовать данные двух лучей антенны;
- результат пеленгования должен отображаться на AntennaIndicator цветом соответствующего BandItem;
- результат пеленгования должен записываться в итоговую таблицу;
- алгоритм пеленгования должен быть изолирован в отдельном сервисе, чтобы его можно было дорабатывать без изменения UI.

## 6. Пользовательский интерфейс

### 6.1. Общая компоновка

SiriusScope должен иметь одно главное окно.

Компоновка главного окна:

```text
+--------------------------------------------------------------+
| MenuBar / Toolbar                                            |
+------------------------------------------+-------------------+
| SpectrumView                             | AntennaIndicator  |
|                                          |                   |
+------------------------------------------+                   |
| WaterfallView                            |                   |
|                                          +-------------------+
|                                          | ResultTable       |
|                                          |                   |
+------------------------------------------+-------------------+
| StatusBar                                                    |
+--------------------------------------------------------------+
```

Требования к компоновке:

- SpectrumView и WaterfallView располагаются слева;
- AntennaIndicator и итоговая таблица располагаются справа;
- нижняя часть окна по всей ширине занята StatusBar;
- верхняя часть окна занята MenuBar / Toolbar;
- примерное соотношение ширины левой и правой областей: 70% / 30%;
- дополнительные окна допустимы только для настройки BandItem;
- окно настройки BandItem должно быть поверх главного окна SiriusScope.

### 6.2. Режим отображения

SiriusScope должен быть рассчитан на работу в полноэкранном режиме на одном мониторе.

Требования:

- поддержка работы в оконном режиме допускается;
- минимальный размер окна должен быть большим, чтобы исключить разрушение компоновки;
- произвольное изменение размеров всех виджетов пользователем не входит в текущую итерацию;
- интерфейс должен быть строго рассчитан на один монитор.

### 6.3. Темная тема

SiriusScope должен обязательно поддерживать темную тему.

Требования:

- цветовая гамма WaterfallView должна быть читаемой на темном фоне;
- цвета BandItem должны быть различимыми на темном фоне;
- цвета BandItem должны использоваться в AntennaIndicator для отображения результатов пеленгования;
- элементы интерфейса должны сохранять читаемость при длительной работе оператора.

## 7. SpectrumView и BandItem

### 7.1. Назначение SpectrumView

SpectrumView является одним из главных виджетов SiriusScope. Он отвечает за отображение частотной области и настройку частотных диапазонов приема, которые передаются в БЦО.

Требования:

- SpectrumView должен показывать частотную шкалу в МГц;
- SpectrumView должен четко показывать частоты, на которых находятся BandItem;
- SpectrumView должен отображать 5 BandItem в текущей версии;
- SpectrumView не должен позволять оператору добавлять или удалять BandItem в текущей версии;
- архитектурно должна быть поддержана возможность другого количества BandItem в будущих версиях;
- SpectrumView должен управлять отображаемым диапазоном WaterfallView.

### 7.2. Управление мышью

Требования:

- прокрутка колесика мыши изменяет масштаб частотной шкалы;
- перемещение мышью при зажатом колесике перемещает видимый частотный диапазон по горизонтали;
- модификаторы клавиатуры для этих действий не требуются;
- при изменении масштаба или позиции частотного диапазона WaterfallView должен сразу перестраивать отображаемую область.

### 7.3. BandItem

BandItem — это не просто визуальный диапазон частот. Архитектурно BandItem представляет один диапазон приема в конфигурации БЦО, а как виджет является способом настройки этого диапазона оператором.

Требования:

- в текущей версии должно отображаться ровно 5 BandItem;
- каждый BandItem соответствует одной полосе БЦО шириной до 500 МГц;
- суммарно 5 BandItem обеспечивают одновременное наблюдение до 2500 МГц;
- у каждого BandItem должен быть собственный неизменяемый цвет;
- цвет BandItem используется в AntennaIndicator для отображения пеленга;
- BandItem не должен иметь пользовательского названия;
- BandItem не должен отображать тип сигнала;
- BandItem не должен иметь пользовательской настройки цвета;
- BandItem не должен иметь статуса активности в текущей версии.

### 7.4. Контекстное меню BandItem

При нажатии правой кнопкой мыши по BandItem должно появляться стандартное контекстное меню рядом с курсором мыши.

Контекстное меню должно содержать один пункт:

- **Настроить**.

При выборе пункта «Настроить» должно открываться окно настроек BandItem.

### 7.5. Окно настроек BandItem

Окно настроек BandItem должно быть модальным или всегда находиться поверх главного окна SiriusScope.

В окне должна быть форма настройки и две кнопки:

- **Отмена**;
- **Сохранить**.

Форма должна содержать следующие поля:

| Поле | Тип элемента |
|---|---|
| Начальная частота диапазона | числовое поле |
| Конечная частота диапазона | числовое поле |
| Время стояния на частоте или диапазоне | числовое поле |
| Параметры фильтра | выбор или набор полей, точный состав определяется протоколом БЦО |
| Тип поляризации | выбор: горизонтальная / вертикальная |
| Уровень входного аттенюатора | выпадающее меню |
| Уровень выходного аттенюатора | выпадающее меню |

При нажатии «Сохранить» настройки должны быть переданы в прикладной слой, а далее в адаптер управления БЦО. UI не должен напрямую формировать аппаратные команды. SiriusScope не должен формировать команды РПУ; БЦО самостоятельно применяет полученную конфигурацию к РПУ.

## 8. WaterfallView

### 8.1. Назначение

WaterfallView является ведомым виджетом относительно SpectrumView. Оператор управляет частотным диапазоном и настройками через SpectrumView, а WaterfallView отображает историю сигналов в выбранной частотной области.

### 8.2. Поведение при изменении SpectrumView

Требования:

- WaterfallView должен сразу перестраивать отображаемую область при изменении диапазона в SpectrumView;
- старые строки водопада должны сохраняться;
- при изменении частотного диапазона старые строки должны визуально пересэмплироваться в новую систему координат;
- если часть старых данных выходит за текущий диапазон, она должна визуально уходить за границы отображаемой области;
- очищать водопад при изменении диапазона запрещается.

Пример: если оператор сдвигает диапазон SpectrumView влево, старые строки в WaterfallView должны визуально сдвинуться вправо или выйти за видимую область.

### 8.3. Направление движения

WaterfallView должен двигаться сверху вниз, от SpectrumView вниз, визуально создавая эффект вытекания данных из SpectrumView.

Ожидаемая скорость движения водопада — примерно **1 строка в секунду**.

### 8.4. Глубина истории

Глубина истории водопада должна быть настраиваемой величиной. Настройка должна задаваться по времени, а не только по числу строк.

### 8.5. Прокрутка истории

WaterfallView должен поддерживать прокрутку колесиком мыши вверх и вниз для просмотра исторических данных.

Требования:

- слева от WaterfallView должна отображаться вертикальная шкала времени;
- шкала должна показывать дату и время принятого сигнала в формате текущего системного времени;
- при прокрутке к старым данным WaterfallView должен заранее подгружать данные из файлов;
- подгрузка должна позволять просматривать данные за несколько дней назад;
- оператор должен визуально понимать по шкале времени, что он домотал до другого дня.

### 8.6. Пауза SiriusScope

Пауза должна применяться не только к WaterfallView, а ко всему SiriusScope.

Требования:

- оператор может поставить SiriusScope на паузу, чтобы рассмотреть историю;
- во время паузы оператор может изменять настройки;
- изменение настроек также допускается во время работы;
- постановка на паузу не должна повреждать архив и сохраненные данные.

### 8.7. Отображение BandItem на WaterfallView

Полупрозрачные прямоугольники BandItem на WaterfallView в текущей версии не требуются, так как они будут создавать визуальный шум.

WaterfallView должен быть чистым спектрально-временным отображением без наложения прямоугольников BandItem.

## 9. Цветовая модель WaterfallView

### 9.1. Общий принцип

Цвет точки или ячейки WaterfallView должен зависеть от:

- амплитуды сигнала;
- разницы амплитуд по двум лучам антенны.

Текущая версия реализуется только для антенны с двумя лучами: `beamIndex = 0` и `beamIndex = 1`.

### 9.2. Входные значения для цветовой модели

Для каждой частотно-временной ячейки WaterfallView должны быть подготовлены агрегированные значения:

```text
A0 — амплитуда по лучу 0
A1 — амплитуда по лучу 1
```

Допустимые амплитуды входных отсчетов: 1–127 условных единиц.

Если по одному из лучей в данной ячейке нет отсчета, значение для этого луча считается отсутствующим для расчета цветовой модели. В текущей версии не требуется отдельная специальная визуальная обработка случая «сигнал только на одном луче».

### 9.3. Нормализация амплитуды

Для расчета уровня сигнала используется максимальная амплитуда по двум лучам:

```text
A = max(A0, A1)
```

Нормированная амплитуда:

```text
An = clamp((A - 1) / 126, 0, 1)
```

Где:

- `A` — амплитуда в условных единицах;
- `An` — нормированное значение амплитуды;
- `clamp` ограничивает значение диапазоном от 0 до 1.

### 9.4. Оценка разницы по лучам

Для оценки преобладания одного луча над другим используется нормированная разница:

```text
D = (A0 - A1) / (A0 + A1)
```

Где:

- `D` близко к `+1`, если преобладает луч 0;
- `D` близко к `-1`, если преобладает луч 1;
- `D` близко к `0`, если амплитуды по двум лучам близки.

Если знаменатель равен нулю или значения отсутствуют, ячейка считается пустой и не должна отображаться как полезный сигнал.

### 9.5. Принцип выбора цвета

Цветовая модель должна иметь два базовых направления цвета:

- цветовая область луча 0;
- цветовая область луча 1.

Нормированная разница `D` определяет смещение цвета между этими областями. Нормированная амплитуда `An` определяет выраженность отображаемого сигнала.

Точные RGB-значения базовых цветов должны быть выбраны при реализации с учетом темной темы и читаемости WaterfallView. Цветовая модель не должна использовать прозрачность как обязательный элемент отображения.

### 9.6. Легенда

Отдельная легенда цветов рядом с WaterfallView в текущей версии не требуется.

Обязательной является только вертикальная шкала времени слева от WaterfallView.

## 10. AntennaIndicator и пеленгатор

### 10.1. Назначение

AntennaIndicator должен отображать:

- текущее положение антенны;
- выбранный оператором сектор сканирования;
- процесс прохождения сектора;
- результаты пеленгования по каждому BandItem после завершения сканирования.

### 10.2. Выбор сектора оператором

Оператор должен иметь возможность выделить сектор мышью на пеленгаторе.

После выделения сектора SiriusScope должен:

1. передать команду управления поворотным устройством через соответствующий аппаратный адаптер;
2. выполнить вращение антенны до прохождения всего выбранного сектора;
3. собрать данные БЦО в процессе прохождения сектора;
4. вычислить пеленг для каждого BandItem;
5. отобразить результат пеленгования на AntennaIndicator;
6. записать результат в итоговую таблицу и архив.

### 10.3. Отображение результатов

Требования:

- пеленг должен отображаться отдельно для каждого BandItem;
- цвет отображения пеленга должен совпадать с неизменяемым цветом соответствующего BandItem;
- хранение полной истории обнаружений на пеленгаторе не требуется в текущей версии;
- связь пеленга со строками WaterfallView и строками итоговой таблицы по клику не требуется в текущей версии;
- связь пеленга с BandItem по цвету обязательна.

### 10.4. Несколько ИРИ

После сканирования выбранного сектора AntennaIndicator должен уметь отображать несколько результатов пеленгования — по одному или нескольким BandItem.

В текущей версии результаты отображаются как пеленги по BandItem. Расширенное сопровождение нескольких ИРИ во времени относится к перспективному развитию.

---

## 11. Итоговая таблица

### 11.1. Назначение

В SiriusScope не требуется таблица импульсов в текущей версии. Вместо нее должна быть итоговая таблица результатов после сканирования сектора.

### 11.2. Состав данных

Итоговая таблица должна содержать:

| Поле | Описание |
|---|---|
| Глобальное время | Дата и время результата с точностью до секунды. |
| Азимут антенны | Азимут, связанный с результатом сканирования. |
| Набор частот | Частоты, связанные с соответствующим BandItem и результатом пеленгования. |

Остальные параметры могут быть добавлены в будущих версиях.

### 11.3. Поведение таблицы

Требования:

- пользователь не должен изменять данные итоговой таблицы;
- сортировка, фильтрация и экспорт не входят в текущую итерацию;
- таблица должна загружаться при запуске SiriusScope;
- при запуске SiriusScope таблица должна показывать прошлые сохраненные данные;
- таблица должна быть всегда заполненной, если в архиве есть данные;
- оператор должен иметь возможность прокручивать таблицу и просматривать данные, записанные в файлах.

## 12. StatusBar

### 12.1. Назначение

StatusBar должен располагаться внизу главного окна по всей ширине.

Он заменяет отдельные журналы и списки событий в текущей версии.

### 12.2. Отображаемая информация

StatusBar должен отображать:

- статус программы;
- статус подключения к БЦО;
- статус подключения к поворотному устройству;
- статус управления БЦО;
- статус применения конфигурации приема, если БЦО предоставляет такую диагностику;
- последние ошибки;
- последние диагностические сообщения;
- текущий азимут антенны;
- статус записи данных;
- краткую информацию о потоке данных, если это необходимо для диагностики.

Отдельный пользовательский журнал событий в интерфейсе не требуется в текущей версии, но технический лог должен сохраняться в файлы.

## 13. Хранение данных

### 13.1. Общий принцип

SiriusScope должен сохранять данные между запусками программы. После запуска оператор должен иметь доступ к ранее записанным строкам WaterfallView и итоговой таблице.

Непрерывная запись должна быть включена всегда.

### 13.2. Что сохранять

Между запусками SiriusScope должны сохраняться:

- строки WaterfallView;
- итоговая таблица;
- настройки программы;
- метаданные записей;
- служебные индексы для быстрой прокрутки истории;
- технические логи.

### 13.3. Форматы хранения

Требования текущей итерации:

- строки WaterfallView хранить в бинарных файлах;
- данные итоговой таблицы хранить в бинарных файлах;
- настройки программы хранить в конфигурационных файлах INI или JSON;
- рабочие данные и архивы не хранить внутри исполняемого файла;
- структура хранения должна обеспечивать быструю последовательную запись и чтение истории при прокрутке.

Рекомендуемая структура данных:

```text
SiriusScopeData/
    settings/
        app_settings.ini или app_settings.json

    recordings/
        2026-04-30_12-00-00/
            metadata.json
            waterfall.bin
            result_table.bin
            signal_data.bin
            config_snapshot.json
            technical.log

    logs/
        app_2026-04-30.log

    cache/
        waterfall_preview/
        temp_indexes/
```

### 13.4. Метаданные записи

Для каждой записи должны сохраняться метаданные:

- идентификатор записи;
- время начала записи;
- время окончания записи, если применимо;
- версия формата архива;
- версия SiriusScope;
- параметры TimeBase;
- количество BandItem;
- параметры частотных диапазонов;
- путь к бинарным данным;
- настройки на момент записи;
- информация о потерях пакетов и ошибках, если они были обнаружены.

### 13.5. Ротация файлов

SiriusScope должен выполнять ротацию файлов.

Требования:

- ротация выполняется по количеству файлов;
- максимальное количество хранимых файлов задается в настройках программы;
- самые старые файлы должны удаляться или освобождать место для новых;
- ротация не должна нарушать целостность текущей записи;
- при удалении старых файлов должны обновляться индексы истории.

### 13.6. Подгрузка данных при прокрутке

При прокрутке WaterfallView и итоговой таблицы SiriusScope должен заранее подгружать данные из файлов.

Требования:

- подгрузка должна выполняться асинхронно;
- прокрутка интерфейса не должна блокироваться операциями чтения с диска;
- должны использоваться служебные индексы или метаданные для быстрого поиска нужного временного диапазона;
- отсутствие кэша не должно приводить к невозможности запуска программы.

## 14. Настройки программы

### 14.1. Общие требования

Настройки программы должны храниться в INI или JSON.

Ядро SiriusScope не должно напрямую зависеть от QSettings, QString, QVariant и других Qt-типов без необходимости. Если используется QSettings, он должен быть скрыт за абстрактным интерфейсом хранилища настроек.

Пример интерфейса:

```cpp
class ISettingsStorage
{
public:
    virtual ~ISettingsStorage() = default;
    virtual AppSettings load() = 0;
    virtual void save(const AppSettings& settings) = 0;
};
```

### 14.2. Состав настроек

В настройках должны храниться:

- максимальное количество файлов архива;
- глубина истории WaterfallView по времени;
- путь к каталогу данных SiriusScope;
- режим подключения: аппаратура или имитационный генератор;
- сетевые параметры подключения;
- параметры отображения SpectrumView;
- параметры отображения WaterfallView;
- выбранная тема интерфейса;
- технические параметры логирования.

Повреждение или отсутствие файла настроек не должно приводить к невозможности запуска SiriusScope. В таком случае программа должна использовать значения по умолчанию.

## 15. Производительность и надежность

### 15.1. Производительность

Требования:

- частота обновления интерфейса: не менее 30 FPS;
- ожидаемая скорость WaterfallView: примерно 1 строка в секунду;
- входной поток данных от БЦО: до 90 МБ/с;
- UDP-пакеты БЦО: около 1500 байт;
- количество BandItem в текущей версии: 5;
- SiriusScope должен сохранять отзывчивость интерфейса при приеме, обработке, отображении и записи данных.

### 15.2. Устойчивость к ошибкам

SiriusScope должен корректно обрабатывать:

- потерю TCP-соединения с поворотным устройством;
- отсутствие UDP-данных от БЦО;
- некорректные значения амплитуды;
- неподдерживаемую версию протокола;
- переполнение или задержки очередей обработки;
- ошибки записи на диск;
- отсутствие или повреждение файла настроек;
- отсутствие кэша.

Ошибки должны отображаться в StatusBar и записываться в технический лог. Ошибка одного модуля не должна приводить к аварийному завершению всей программы, если возможно безопасное продолжение работы.

## 16. Тестовый генератор сигналов

### 16.1. Назначение

Для тестирования SiriusScope должен использоваться тестовый генератор сигналов, представляющий собой полную программную имитацию аппаратуры.

Генератор должен имитировать:

- БЦО, включая прием управляющей конфигурации и внутреннюю имитацию управления РПУ;
- поворотное устройство антенны / СВБ.

### 16.2. Требования

Тестовый генератор должен использовать тот же протокол, что и реальная аппаратура.

SiriusScope должен работать с генератором так же, как с реальным изделием, без изменения бизнес-логики и UI.

Генератор должен позволять проверять:

- отображение сигнала на SpectrumView;
- отображение сигнала на WaterfallView;
- получение текущего азимута;
- сканирование сектора;
- отображение пеленга на AntennaIndicator;
- запись строк WaterfallView;
- запись итоговой таблицы;
- восстановление данных после перезапуска SiriusScope;
- устойчивость при нагрузке.

## 17. Тестирование

### 17.1. Покрытие тестами

Исходный код SiriusScope должен быть покрыт автоматизированными тестами не менее чем на 50%.

### 17.2. Виды тестов

Должны быть реализованы:

- модульные тесты доменных структур и сервисов;
- тесты парсеров протоколов;
- тесты обработки некорректных данных;
- тесты модели времени;
- тесты хранения и чтения бинарных файлов;
- тесты ротации файлов;
- тесты настройки BandItem и формирования конфигурации БЦО;
- интеграционные тесты с тестовым генератором;
- нагрузочные тесты входного потока до 90 МБ/с;
- UI-тесты критических сценариев, если это технически оправдано.

### 17.3. Критерии приемки

Обязательные критерии приемки:

1. Сигнал отображается на SpectrumView.
2. Сигнал отображается на WaterfallView после сканирования сектора на AntennaIndicator.
3. Пеленг отображается на AntennaIndicator.
4. Интерфейс не замораживается при приеме, обработке, отображении и записи данных.
5. Данные WaterfallView сохраняются между запусками программы.
6. Итоговая таблица сохраняется между запусками программы.
7. При запуске SiriusScope загружаются прошлые данные WaterfallView и итоговой таблицы.
8. Программа работает как с реальной аппаратурой, так и с имитационным генератором через одинаковые интерфейсы.
9. Покрытие кода тестами составляет не менее 50%.

Сравнение SiriusScope со старым ПО не является критерием приемки, так как SiriusScope разрабатывается как принципиально новый программный продукт.

## 18. Требования к безопасности и отказоустойчивости

### 18.1. Безопасность данных

SiriusScope должен обеспечивать сохранность записываемых данных при штатной работе.

Требования:

- запись данных должна выполняться последовательно и устойчиво к кратковременным сбоям отдельных модулей;
- при невозможности записи на диск ошибка должна отображаться оператору;
- повреждение одного архивного файла не должно приводить к невозможности запуска SiriusScope;
- настройки должны иметь значения по умолчанию;
- кэш должен быть восстанавливаемым и не должен считаться критичными данными.

### 18.2. Отказоустойчивость интерфейса

GUI должен оставаться отзывчивым при:

- максимальном входном потоке;
- длительной записи;
- прокрутке WaterfallView по архиву;
- ошибках аппаратного подключения;
- чтении старых данных из файлов.

### 18.3. Диагностика

SiriusScope должен вести технический лог, достаточный для диагностики:

- ошибок подключения;
- ошибок парсинга протоколов;
- потери пакетов;
- некорректных входных значений;
- ошибок записи и чтения файлов;
- превышения допустимых задержек обработки.

## 22. Краткое резюме требований

SiriusScope должен быть новым кроссплатформенным программным комплексом на C++/Boost/Qt/QML/CMake/Conan, объединяющим управление БЦО и поворотным устройством, прием данных, визуализацию, хранение и пеленгование. Программа должна работать с аппаратурой и имитационным генератором через одинаковые интерфейсы, передавать в БЦО конфигурацию приема для 5 BandItem, не взаимодействовать с РПУ напрямую, принимать данные от БЦО по UDP и азимут от поворотного устройства по TCP, отображать 5 BandItem в SpectrumView, вести WaterfallView сверху вниз со скоростью около одной строки в секунду, выполнять сканирование выбранного сектора на AntennaIndicator, показывать пеленг по каждому BandItem, непрерывно сохранять данные в бинарные файлы и загружать историю между запусками. Интерфейс должен оставаться отзывчивым при входном потоке до 90 МБ/с, а исходный код должен быть покрыт тестами не менее чем на 50%.

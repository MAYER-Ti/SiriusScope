# SBCO UDP v1: генератор ↔ SiriusScope

Реализованный протокол **собственного генератора**, версия 1. Спецификация пакетов
реальной аппаратуры БЦО пока не предоставлена; совместимость с ней не заявляется.
Кодек: `modules/bco-generator/include/bco_generator/protocol.h` и `src/protocol.cpp`.
Сериализация явная, big endian; C++-структуры в сеть не копируются.

## Размер пакета

Под «1500 Б» здесь принят MTU IPv4 без IP options:

```text
20 IPv4 + 8 UDP + 80 SBCO header + 87 × 16 sample = 1500 bytes
                   └──────── UDP payload 1472 ────────────┘
```

1500 байт именно UDP payload дали бы IP-пакет 1528 байт и фрагментацию при MTU 1500.
Последний пакет блока короче, без padding: `80 + count × 16`. Пустой DATA содержит
80 байт и служит heartbeat, например между импульсами. Данные одного отсчёта никогда
не разбиваются между пакетами; пара лучей может оказаться в разных пакетах.
Ethernet header/FCS/preamble/inter-frame gap в MTU не входят.

Избегание IP-фрагментации и учёт заголовков соответствуют
[RFC 8085 §3.2](https://www.rfc-editor.org/rfc/rfc8085.html#section-3.2);
[UDP header](https://www.rfc-editor.org/rfc/rfc768.html) занимает 8 байт.
Linux/Windows host-адаптер запрашивает запрет фрагментации. В v1 поддержан только IPv4;
MTU пути должен быть не меньше 1500. Туннели/меньший MTU требуют отдельной настройки
размера пакетов в следующей версии транспорта; автоматического PMTU discovery нет.

## Общий заголовок — 80 байт

Смещения отсчитываются от начала UDP payload. Все многобайтовые поля big endian;
знаковые поля — two's complement. Reserved/flags обязаны быть нулевыми.

| Offset | Bytes | Поле | Значение |
|---:|---:|---|---|
| 0 | 4 | magic | ASCII `SBCO`, `0x5342434f` |
| 4 | 1 | version | 1 |
| 5 | 1 | kind | DATA=1, SUBSCRIBE=2, STOP=3 |
| 6 | 2 | headerBytes | 80 |
| 8 | 8 | stream | Ненулевой ID подписки, новый при каждом старте приёмника |
| 16 | 8 | sequence | DATA: номер датаграммы от 0; control: возрастающий номер запроса |
| 24 | 8 | producer | DATA: ненулевой ID запуска генератора; control: 0 |
| 32 | 8 | firstSampleIndex | Начало timebase записи, **не** первый отсчёт пакета |
| 40 | 8 | samplePeriodNs | Период исходного индекса в нс, >0 |
| 48 | 8 | startUtcNs | UTC начала записи, Unix ns, 0..INT64_MAX |
| 56 | 4 | revision | Ненулевая версия конфигурации |
| 60 | 4 | azimuthMilliDeg | int32: 0..359999, либо -1 (неизвестен) |
| 64 | 2 | count | Число записей после заголовка |
| 66 | 2 | recordBytes | DATA=16, SUBSCRIBE=40, STOP=0 |
| 68 | 4 | flags | 0 |
| 72 | 8 | reserved | 0 |

Длина датаграммы обязана точно совпадать с `80 + count × recordBytes` и быть ≤1472.
`sequence=UINT64_MAX` запрещён; до исчерпания счётчика требуется новый stream.
ID в host-реализации основаны на часах и монотонном счётчике процесса; это не
криптографические идентификаторы и не механизм аутентификации.

## DATA: 0..87 записей по 16 байт

| Offset внутри записи | Bytes | Поле | Ограничение |
|---:|---:|---|---|
| 0 | 8 | sampleIndex | Исходный uint64 индекс БЦО, ≥firstSampleIndex |
| 8 | 4 | frequencyOffsetHz | int32, −250000000..250000000 Гц |
| 12 | 1 | bandIndex | 0..7 в формате |
| 13 | 1 | beamIndex | 0..7 в формате |
| 14 | 1 | amplitude | 1..127; 0 недопустим |
| 15 | 1 | reserved | 0 |

Индексы внутри датаграммы не убывают; повтор одного индекса для разных лучей допустим.
Абсолютная частота = согласованный центр полосы + offset. SiriusScope дополнительно
проверяет включённую полосу, попадание в её ширину и текущие два луча 0/1.
UI использует текущие пять полос; резерв формата до восьми не включает новые
продуктовые возможности автоматически. Время вычисляется штатным TimeBase, не временем
получения пакета. `producedAt` блока приёмника — локальный steady-clock RX timestamp;
это не измерение задержки от устройства до хоста.

## SUBSCRIBE: 1..8 записей по 40 байт

| Offset внутри записи | Bytes | Поле |
|---:|---:|---|
| 0 | 1 | bandIndex, уникальный 0..7 |
| 1 | 1 | enabled, 0/1 |
| 2 | 1 | pulsed, 0/1 |
| 3 | 1 | reserved=0 |
| 4 | 4 | widthHz, 1..500000000 |
| 8 | 8 | centerHz; вся полоса внутри 0.3..18 ГГц |
| 16 | 8 | pulsePeriodNs, при pulsed: >pulseWidthNs и ≤60 секунд |
| 24 | 8 | pulseWidthNs, при pulsed: >0 |
| 32 | 8 | reserved=0 |

При pulsed=0 поля PRI/PW игнорируются. В текущем совместимом адаптере невалидные
настройки импульса дают continuous; отдельного подтверждения ошибки от сервера нет.
Азимут передаётся в заголовке, чтобы удалённый имитатор использовал положение
виртуальной антенны SiriusScope. При -1 host-генератор использует 0°.

## Обмен и жизненный цикл

1. Генератор слушает `127.0.0.1:46001`, но ничего не шлёт без подписки.
2. При старте записи RX-поток SiriusScope привязывает UDP-сокет (по умолчанию
   `0.0.0.0:46000`), выбирает новый stream и посылает SUBSCRIBE. Текущие полосы,
   TimeBase, PRI/PW и азимут передаются этому генератору.
3. SUBSCRIBE повторяется каждые 100 мс с возрастающим control sequence.
   DATA направляется на IP/порт отправителя подписки с порта генератора.
   Генератор поддерживает одного подписчика; иной endpoint/stream отклоняется,
   пока действует аренда текущего подписчика.
4. Lease по умолчанию 1 с. При отсутствии новых SUBSCRIBE отправка прекращается.
   Та же подписка может возобновиться с сохранением индексов и DATA sequence.
   Новый stream после истечения lease сбрасывает индексы и sequence.
5. `firstSampleIndex`, `samplePeriodNs`, `startUtcNs` неизменны внутри stream.
   Версия конфигурации не может уменьшаться. PRI/PW/enabled обновляются через revision;
   обновление азимута не меняет revision. Первые DATA с соответствующим stream/revision
   показывают применение настроек; отдельного ACK нет. Приёмник отбрасывает старую
   revision после отправки новой.
6. STOP — заголовок без записей, с тем же stream и следующим control sequence.
   Приёмник повторяет STOP три раза. При потере всех копий действует lease.
   Генератор помнит 64 завершённых stream, чтобы запоздавшие SUBSCRIBE не возобновили
   недавно остановленную запись. Это ограниченная защита от задержанных пакетов.
7. Приёмник фиксирует producer первого корректного DATA. Перезапуск генератора
   меняет producer: для продолжения нужно остановить и заново начать запись.
   Пакеты другого производителя не склеиваются с текущей записью.

`start()` приёмника подтверждает только локальный bind/создание RX-потока;
`UdpBcoControl` подтверждает локальную конфигурацию, не удалённый запуск аппаратуры.
Если подходящих DATA нет 1 с, публикуется агрегированное предупреждение.

## Потери, память и нагрузка

- UDP не гарантирует доставку. Повторной передачи DATA нет. Разрыв sequence учитывается
  как missing; дубликаты и запоздавшие/reordered датаграммы отбрасываются. Reorder-buffer
  отсутствует; позднее прибытие не уменьшает missing. Потерю хвоста без следующего
  пакета определить по sequence невозможно.
- Неверная версия, длина, reserved или данные приводят к отклонению всей датаграммы.
  Проверка checksum выполняется UDP/IP-стеком ОС; дополнительного CRC в SBCO нет.
- RX использует 32 заранее выделенных блока по 8192 `SignalSample`. Пакеты агрегируются
  до 8192 записей либо примерно 10 мс; смена азимута также завершает блок. При занятых
  блоках новые данные отбрасываются с учётом poolExhaustions/droppedSamples.
  Далее работают существующие ограниченные очереди/пулы конвейера SiriusScope.
- Метрики источника: accepted UDP payload bytes/s, samples/s, missing, malformed;
  дополнительные networkMetrics: datagrams, late, foreign, receive/control-send errors,
  poolExhaustions. Предупреждения агрегируются не чаще раза в секунду.
- Полный пакет несёт 1392 байта записей; 80 байт заголовка — около 5.4% UDP payload.
  `--rate` задаёт бюджет слотов/записей в секунду по контракту ядра, не MB/s.
  Между импульсами фактическая передача меньше. Без PRI/PW используется legacy fast path,
  с PRI/PW — физическая модель; различия описаны в README ядра.
- Host-генератор дозирует отправку блоками 10 мс, от 100000 slots/s — 1 мс.
  Начало окна переводится из монотонного времени подписки в исходный `sampleIndex`
  через согласованный `samplePeriodNs`. Малая скорость выдачи не замедляет часы БЦО.
  Просроченные окна пропускаются; keepalive и возобновление той же подписки сохраняют
  эпоху. Новый stream начинает новую временную шкалу.
- Размер выдачи ограничен бюджетом `--rate` (округление вниз на пачку) и числом тактов
  БЦО в текущем окне: при 320 нс верхняя граница 3 125 000 slots/s. Поэтому большие
  бюджеты не создают перекрывающиеся индексы и не ускоряют модельное время.
  При малой скорости выбирается лишь начало каждого окна; короткие импульсы могут
  быть пропущены, точная оценка PW в таком режиме не гарантируется. Это мягкое
  планирование обычной ОС, не гарантия темпа реальной embedded-платы.

Текущий транспорт рассчитан на выделенную/доверенную LAN. Шифрование, аутентификация,
автоматический congestion control, multicast, IPv6, аппаратный control protocol и
синхронизация часов устройства не реализованы. Для публичной/разделяемой сети нужны
дополнительные механизмы. Прохождение loopback-тестов не доказывает устойчивую работу
на 60–90 MB/s через физический Ethernet; это отдельное нагрузочное измерение.

## Сборка и запуск

Из корня репозитория, без Qt для отдельного генератора:

```sh
cmake -S modules/bco-generator -B build/bco-generator-host -DCMAKE_BUILD_TYPE=Release
cmake --build build/bco-generator-host
ctest --test-dir build/bco-generator-host --output-on-failure
build/bco-generator-host/bco-generator --bind 127.0.0.1 --port 46001 --rate 1280
```

В другом терминале после сборки SiriusScope:

```sh
build/Desktop_Qt_6_11_2_Debug/appSiriusScope --bco-udp-host 127.0.0.1 --bco-udp-port 46001 --bco-bind-port 46000
```

Для двух машин генератор привязывается к своему LAN IPv4 через `--bind`, а SiriusScope
получает этот адрес в `--bco-udp-host`. Нужен двусторонний UDP между выбранными портами.
Имена DNS не поддержаны. `--bco-bind-port 0` выбирает свободный локальный порт.
После запуска приложения начните запись/сканирование штатной командой интерфейса.
Для первой проверки задайте центр полосы **3000 МГц**, ширину **500 МГц** и азимут
**0°**: в этой полосе виден источник **2920 МГц**. Остальные частоты сцены — 5825,
8250, 9670 и 14190 МГц. `--rate 1280` — скорость выдачи, а не частота сигнала;
полоса с центром 9300 МГц и шириной 500 МГц не захватывает источник 9670 МГц.

Источник выбирается меню «Генератор / Аппаратура / Контроль»:

- **Генератор** — встроенный источник SiriusScope с обычным профилем
  `BaselineRawThroughput60MBps`.
- **Аппаратура** — приём SBCO UDP v1 от отдельного процесса `bco-generator`.
  По умолчанию адрес генератора `127.0.0.1:46001`, локальный порт `46000`.
  После включения записи/сканирования приёмник подписывается и ждёт DATA;
  генератор можно запустить позднее. Подмены отсутствующих данных встроенным
  генератором нет. Статус различает «ожидание данных» и «приём данных».
- **Контроль** — приём и генерация отключены, запуск записи/сканирования недоступен;
  просмотр сохранённых данных остаётся доступен. Аппаратная самодиагностика не реализована.

Смена источника разрешена между сеансами записи/сканирования и сохраняет настройки
полос и импульсов. QML-модели, контроллеры и общий data plane не пересоздаются.
Без сетевых параметров используется сохранённый режим (при отсутствии настройки —
«Генератор»). Любой явно заданный `--bco-udp-host`, `--bco-udp-port` или
`--bco-bind-port` выбирает начальный режим «Аппаратура» и задаёт его endpoint;
после запуска можно переключаться меню. Совместимость с протоколом реальной
аппаратуры этой интеграцией не заявляется.

## Проверки

`tst_bco_protocol`: эталонный byte order, полные/короткие/пустые пакеты, все усечения,
невалидные поля, ограниченные output buffers, SUBSCRIBE/STOP, sequence gaps/reordering.
`tst_udp_bco_stream_source`: реальные IPv4 loopback-сокеты, перезапуск записи,
повреждённые/чужие/дублированные пакеты, исчерпание пула, stop quiescence и доставка
через BcoAcquisitionSession до обработки. В том же тесте запускается отдельный процесс
`bco-generator` с 100000 slots/s, проверяются контроль PRI/PW/enabled и передача в pipeline.
`tst_application_bootstrap` проверяет выбор UDP-адаптеров вместо встроенного источника.

Для embedded используйте `BCO_GENERATOR_BUILD_HOST=OFF`: остаются ядро и безаллокирующий
кодек. Socket, часы, scheduler и выдачу датаграмм реализует платформенный runner;
перенос самого host socket adapter на плату не требуется.

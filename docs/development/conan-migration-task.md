# Задача: Полный перевод SiriusScope на Conan

## Контекст

В проекте уже добавлен базовый `conanfile.py`, но Conan используется частично: отсутствует полноценный граф зависимостей, а сборка допускает обходной сценарий без `conan install`.

Цель этой задачи — завершить переход к **Conan-first** процессу сборки, чтобы локальная и CI-сборка были воспроизводимыми и единообразными.

## Цель

Сделать Conan обязательной и единственной точкой управления внешними зависимостями и toolchain-конфигурацией для проекта.

## Область работ

### 1) Привести `conanfile.py` к production-формату

- Добавить `package_type = "application"`.
- Ввести `layout()` через `cmake_layout(self)`.
- Добавить `options` и `default_options` (по необходимости: `shared`, `fPIC`, другие релевантные).
- Добавить `requires` для всех реально используемых внешних библиотек.
- При необходимости добавить `tool_requires` для воспроизводимого toolchain.
- Зафиксировать версии зависимостей и policy обновления.

### 2) Перевести разрешение зависимостей CMake на Conan

- Обеспечить, что `find_package(...)` резолвится через `CMakeDeps` Conan.
- Согласовать версии Qt из Conan с требованиями проекта в CMake (`qt_standard_project_setup`).
- Исключить неявную зависимость от случайных системных путей.

### 3) Стандартизировать CMake Presets

- Добавить/обновить репозиторный `CMakePresets.json` для Conan workflow.
- Оставить `CMakeUserPresets.json` только для локальных override, без критичных путей.
- Зафиксировать единый сценарий: `conan install` → `cmake configure` с toolchain → `build` → `test`.

### 4) Воспроизводимость: profiles и lockfiles

- Добавить поддерживаемые Conan host/build profiles.
- Добавить lockfile-практику (генерация, хранение, обновление).
- Зафиксировать список remotes и порядок их использования.

### 5) Conan-first в CI

- Добавить шаги Conan в CI pipeline:
  - настройка профилей;
  - `conan install`;
  - configure через `CMAKE_TOOLCHAIN_FILE`;
  - build/test.
- Добавить кэш Conan для ускорения.
- Добавить guard: CI должен падать при обходе Conan toolchain.

### 6) Обновить документацию

- Обновить `docs/development/build-and-test.md`:
  - сделать Conan обязательным для рабочих сценариев;
  - убрать/пометить legacy-путь без Conan;
  - добавить troubleshooting раздел для типовых Conan/CMake ошибок.
- Обновить `docs/README.md` при необходимости ссылками на новые инструкции.

## Критерии готовности (DoD)

- Любая поддерживаемая локальная сборка проходит через `conan install` и Conan toolchain.
- CI использует Conan-first pipeline во всех целевых конфигурациях.
- Все внешние зависимости объявлены в Conan и воспроизводимы через profiles/lockfile.
- В репозитории есть рабочие presets без ручной правки путей.
- Документация соответствует фактическому процессу и не содержит противоречивых инструкций.

## Ограничения и архитектурные правила

- Не менять модульные и слоевые границы проекта без отдельной задачи.
- Не переносить инфраструктурную/протокольную/обрабатывающую логику в UI/QML.
- Не ухудшать отзывчивость GUI-потока.

## Риски

- Ограниченная доступность бинарных пакетов Qt для некоторых платформ.
- Несовместимость существующих локальных окружений с фиксированными Conan profiles.
- Рост времени первых сборок без корректного кэширования в CI.

## Предлагаемый порядок выполнения

1. Подготовка `conanfile.py`.
2. Обновление CMake/presets.
3. Введение profiles/lockfile/remotes policy.
4. Подключение Conan-first CI.
5. Актуализация документации и финальная валидация на чистом окружении.

# Переносимое ядро генератора БЦО

Самостоятельный C++20/CMake-проект внутри SiriusScope, без Qt и файлов SiriusScope.
`BcoGenerator::Core` (`bco_generator`) содержит ядро генерации и кодек SBCO UDP v1;
зависит только от стандартной библиотеки и математических функций платформы.
`BcoGenerator::Host` добавляет socket/scheduler и Threads; консольный `bco-generator`
передаёт данные отдельному процессу SiriusScope. На Windows host target использует Winsock.

Из корня SiriusScope:

```sh
cmake -S modules/bco-generator -B build/bco-generator-debug -DCMAKE_BUILD_TYPE=Debug
cmake --build build/bco-generator-debug
ctest --test-dir build/bco-generator-debug --output-on-failure
```

Каталог можно скопировать в отдельный репозиторий и собрать теми же командами с `-S .`.
При подключении через `add_subdirectory` тесты модуля по умолчанию выключены;
SiriusScope регистрирует их в своем наборе CTest. Для cross-compilation передайте
`CMAKE_TOOLCHAIN_FILE`, `BCO_GENERATOR_BUILD_TESTS=OFF` и `BCO_GENERATOR_BUILD_HOST=OFF`.
С выключенным HOST модуль не ищет Threads и не компилирует сетевой код ОС. На конкретной embedded-платформе
сборка и численная точность пока не проверены.

## Контракт

`generate(BatchRequest, span<Sample> output, span<Sample> scratch)` — синхронный шаг:

- сцена, включенные полосы, PRI/PW, индекс начала, начало timebase и азимут передаются явно;
- все spans заимствуются на время вызова, не должны перекрываться;
- ядро не выделяет heap-память, не читает часы, не запускает потоки и не делает I/O;
- состояние времени принадлежит вызывающей стороне: `BatchResult::nextSampleIndex`
  задаёт конец обработанного диапазона слотов; последовательная генерация продолжает
  с него, а host runner может пропускать интервалы по своим часам;
- `output.size()` задает бюджет записей и временных слотов, как в исходном генераторе;
- fastContinuous без PRI/PW требует scratch на две записи для каждого источника сцены;
  при его нехватке возвращается `InsufficientScratch`, без записи в output и продвижения времени;
- `sampleCount` может быть нулём при продвижении времени; нулевой output не продвигает время;
- один запрос можно повторить для воспроизводимого результата без сброса глобального состояния;
- формат `Sample` — локальный C++-контракт, не wire protocol и не сериализуемая память пакета.

Проверка продуктовых ограничений полос остается в вызывающем адаптере: `Band::valid`
содержит ее результат. В ядро не перенесены ограничения UI на пять BandItem, диагностика,
выбор load profile, учет эквивалентных байтов, управление антенной и сеансом записи.

Сохранены явно зафиксированные особенности текущей реализации: физическая модель
выдает два луча на один индекс; нечётный бюджет может обрезать пару и не переносит
остаток в следующий блок. Нагрузочный fast path выдает индекс на каждую запись и
использует фиксированную частоту даже при включенном дрейфе. Невалидный PRI/PW в
совместимом режиме дает непрерывный сигнал; диагностику публикует адаптер.

## Интеграция

`HighLoadSimulatorBcoStreamSource` — адаптер ядра к `IBcoStreamSource`. Он сохраняет
профили нагрузки, потоки/ожидания, снимок конфигурации на блок, диагностику, получение
азимута и метрики. Выход ядра помещается в переиспользуемый рабочий буфер, затем
преобразуется в принадлежащий callback блок `core::SignalSample`. Это дополнительный
проход копирования, который следует учитывать в нагрузочных измерениях; ядро не
зависит от пула памяти SiriusScope. В самом адаптере остаются host-выделения памяти.

Доставка: `IBcoStreamSource → BcoAcquisitionSession → SourceToPipelineBridge →
DataIngestPipeline`. `WaterfallController` видит только `IAcquisitionControl`, не
принимает исходные блоки и не захватывается callback источника. Bootstrap владеет
сессией; источник, pipeline и диагностика живут дольше нее. Закрытие входа синхронизировано
с callback; уничтожение сессии сначала закрывает вход, затем останавливает источник
и очередь. Контракт `stop()` источника требует завершить все callbacks до возврата.

## Сеть

```sh
build/bco-generator-debug/bco-generator --bind 127.0.0.1 --port 46001 --rate 1280
# Во втором терминале:
build/Desktop_Qt_6_11_2_Debug/appSiriusScope --bco-udp-host 127.0.0.1
```

Затем начните запись штатной командой SiriusScope. Генератор принимает SUBSCRIBE
с полосами, TimeBase, PRI/PW и азимутом; отправляет до 87 записей в UDP payload 1472 Б
(IPv4 MTU 1500). `--rate` — slots/s по контракту ядра, `--duration` — необязательное
время работы в секундах. По умолчанию сервер слушает только loopback и одного подписчика.

Индексы начала пачек host runner вычисляет по монотонным часам текущей подписки
и согласованному `samplePeriodNs`, независимо от `--rate`. При стандартных 320 нс
за 10 мс индекс продвигается на 31250 даже при малом бюджете выдачи. Благодаря этому
при запуске без параметров водопад/спектр обновляются во время записи, а PRI/PW
не растягиваются на минуты. При отставании пропускаются просроченные окна; повторные
SUBSCRIBE и возобновление той же подписки не сбрасывают время.

`--rate` — верхний бюджет записей/слотов, а не частота радиосигнала и не частота часов
БЦО. Размер буфера округляется вниз до целого числа записей на пачку и ограничивается
числом тактов БЦО в окне (при 320 нс не более 3 125 000 slots/s). Малый бюджет даёт
короткую выборку в начале каждого окна 10 мс (от 100000 slots/s — 1 мс): очень короткие
импульсы могут быть пропущены, оценка PW при такой разреженной выдаче не является
точной. Это режим проверки интерфейса/транспорта, а не полнота физической выборки.

Частоты сцены фиксированы: 2920, 5825, 8250, 9670 и 14190 МГц; две последние имеют
небольшой дрейф. Для первой проверки используйте полосу с центром 3000 МГц и шириной
500 МГц при азимуте 0°: в ней виден источник 2920 МГц. Значение 1280 в выводе
генератора относится только к скорости, а полоса 9300 ± 250 МГц не содержит 9670 МГц.

Путь данных: `bco-generator → UDP → UdpBcoStreamSource → BcoAcquisitionSession →
SourceToPipelineBridge → DataIngestPipeline`. В SiriusScope выберите «Аппаратура»
и включите запись; для localhost CLI-флаг не обязателен. «Генератор» возвращает
встроенный источник, «Контроль» отключает сбор данных. Явные сетевые CLI-параметры
выбирают начальный режим «Аппаратура». Полное описание пакета, запуска на двух машинах,
управления, потерь и ограничений: [SBCO UDP v1](../../docs/hardware/bco-udp-protocol.md).

`protocol.h` не зависит от socket API, heap или Qt; его можно использовать в embedded
runner вместе с `generator.h`. Реализация runner для конкретной платы — следующий шаг.
